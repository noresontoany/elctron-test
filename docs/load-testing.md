# Нагрузочный стенд Spoke

Цель — измерить цену цепочки **API → PostgreSQL → Electric → proxy → клиент**, отдельно от экономии подписок между вкладками. Готового числа «выдержит N пользователей» здесь нет: оно зависит от частоты изменений, размера данных, числа shapes, клиентов, оборудования и сети.

## Локальный запуск

```bash
make up
make local-ca
```

Основной адрес для нескольких окон — **https://localhost:8447**. Старый **http://127.0.0.1:8097** работает для сравнения. Используйте один и тот же адрес во всех окнах. Caddy слушает только loopback, порты 80/443 других проектов не меняются.

Локальный Caddy выпускает сертификат через собственный CA. `.artifacts/caddy-root.crt` содержит только публичный сертификат CA; импортируйте его как доверенный центр в используемый браузер, если нужен обычный просмотр без предупреждений. Скрипты не меняют системное хранилище доверия. Для Python используйте `--ca .artifacts/caddy-root.crt`. У браузерного benchmark есть `--local-tls`, отключающий проверку сертификата **только в запущенном тестовом Chromium**; для публичного VPS его не используйте.

При изменении `APP_TLS_PORT` обновите `APP_EXTRA_ORIGINS` в `.env`. Порты и корни доверия разных установок независимы. Caddy CA сохраняется в отдельном Docker volume.

## Проверка десяти вкладок

```bash
make bench-tabs BENCH_ARGS='--local-tls --tabs 10 --writes 10 --mode shared --output ../.artifacts/bench/tabs-shared.json'
make bench-tabs BENCH_ARGS='--local-tls --tabs 10 --writes 10 --mode direct --output ../.artifacts/bench/tabs-direct.json'
```

Нужны `cd frontend && npm ci` и Chromium (`/usr/bin/chromium`, `CHROMIUM_PATH` или `npx playwright install chromium`). Скрипт проверяет реальный протокол, открывает вкладки одного пользователя, создаёт заказы через API, ждёт карточку во **всех** вкладках, закрывает лишние и проверяет снятие подписчиков. Созданные UUID удаляются через API с `version=1`; чужие заказы не очищаются. Ошибки очистки выводятся отдельно. Замер DOM включает polling Playwright, поэтому это приблизительная оценка видимости, а не точный paint timer.

Ожидание: 40 подписок вкладок → 4 исходные коллекции в shared, 40 в direct. Число берётся из диагностики настоящих workers, а не оценивается только по сетевым запросам страницы. SharedWorker-запросы могут не отображаться в Network отдельной вкладки.

## Независимые клиенты и скорость записей

`uv` запускает скрипт с собственными зависимостями, включая поддержку HTTP/2:

```bash
# API без активных читателей (Electric при этом продолжает репликацию)
make bench BENCH_ARGS='--url https://localhost:8447 --ca .artifacts/caddy-root.crt --mode api --rate 2 --duration 30'

# Только начальная синхронизация и idle long polling
make bench BENCH_ARGS='--url https://localhost:8447 --ca .artifacts/caddy-root.crt --mode sync --readers 10 --duration 30'

# Запись + подтверждение каждым из 10 независимых читателей
make bench BENCH_ARGS='--url https://localhost:8447 --ca .artifacts/caddy-root.crt --mode e2e --readers 10 --rate 2 --duration 30'
```

`--readers N` означает N независимых устройств по **четыре** shapes: orders/users/teams/team_members. Python не делит их через SharedWorker. Все читают лабораторную мастерскую, поэтому проверяется fan-out одного набора данных. Это не тест N разных арендаторов/уникальных shapes. В режиме e2e перед записями ждём готовность всех начальных снимков.

Записи приходят по фиксированному расписанию. Если занято `--max-inflight` мест, попытка учитывается как `generator_dropped`, а не исчезает из предлагаемой нагрузки. В e2e место занято до доставки всем читателям или таймаута `--timeout`. Отчёт содержит задержку расписания генератора; при её росте предел может быть на стороне генератора. Размещайте генератор на отдельной машине. Для больших нагрузок используйте несколько процессов и отдельные файлы отчёта.

У каждого виртуального устройства свой httpx client/пул. По умолчанию Python-генератор использует **HTTP/1.1, в том числе поверх HTTPS**. У писателя отдельный client: все устройства и записи не сваливаются в один HTTP/2 transport генератора. HTTP/2 сам имеет лимит потоков на соединение, который может ограничить особенно большой `--max-inflight` писателя. `--http-version 2` оставлен как экспериментальный режим. В локальной проверке httpx задерживал данные одного long poll до ответа других потоков (вплоть до 20 секунд), хотя браузерный HTTP/2-тест доставлял те же изменения быстро. Такое поведение обсуждается в [httpx #1766](https://github.com/encode/httpx/discussions/1766). Эти результаты нельзя выдавать за предел Electric; для HTTP/2 используйте также браузерный benchmark. HTTP/1.1 соединения из пула позволяют отдельно исследовать сервер. Это не симуляция сетевых ограничений браузера. У читателя максимум четыре соединения, у писателя — max-inflight + небольшой запас.

### Что в JSON

| Поле | Смысл |
| --- | --- |
| `write_api` | p50/p95/p99 времени POST, только успешные ответы; ошибки рядом |
| `write_to_sync` | от отправки POST до появления его txid в завершённом пакете Electric у каждого читателя |
| `write_to_first_reader`, `write_to_all_readers` | доставка первому и последнему из читателей |
| `api_ack_to_sync` | доставка относительно REST-ответа; может быть отрицательной |
| `delivery_expected/confirmed/missing` | знаменатель, полученные и пропущенные подтверждения |
| `initial_sync` | время первоначальной синхронизации каждой коллекции |
| `generator_dropped`, `generator_schedule_lag` | перегрузка самого генератора |
| `errors`, `shape_resets`, `http_versions` | ошибки по типам/статусам, сбросы, реальный протокол |
| `poll_including_idle` | длительность long poll, **не задержка доставки изменения** |

Подтверждение требует совпадения API txid и txid изменения, плюс `up-to-date`. Парсер учитывает pagination, 204, 409 и must-refetch. Таймауты/пропуски не входят в успешные percentiles: при них код возврата ненулевой, смотреть нужно весь отчёт. API и sync имеют разные распределения — вычитать их p95 друг из друга некорректно. В режиме api невозможно измерить доставку, её счётчики равны нулю.

Каждый запуск создаёт JSON-отчёт и журнал UUID **до отправки** записи. В конце удаляет только свои UUID через API; `version=1` защищает запись, которую кто-то успел изменить. `--keep` оставляет записи для роста датасета. После принудительного завершения/недоступности API могут остаться записи — UUID лежат рядом в `.ids.jsonl`; общую очистку базы скрипт не выполняет. Результаты и журнал не попадают в Git. Для повторного запуска с `--output` выбирайте новое имя: существующий журнал UUID скрипт не перезаписывает.

## Метрики и ограничение proxy

```bash
make metrics
# В отдельном терминале — ресурсы только этого Compose-проекта:
docker stats $(docker compose ps -q)
```

`GET http://api:8000/internal/metrics` доступен внутри Docker-сети в формате Prometheus. Публичный Caddy его не проксирует. Для Prometheus target: `api:8000`, `metrics_path: /internal/metrics`. Не открывайте API-порт наружу ради метрик.

- `spoke_http_seconds{method,route,status}` — длительность API; route шаблонный, UUID не раздувают число рядов.
- `spoke_sync_active`, `spoke_sync_waiting` — занятые слоты и ожидающие.
- `spoke_sync_wait_seconds` — ожидание допуска к Electric.
- `spoke_sync_rejected_total` — отказ 503 при исчерпании слотов.
- `spoke_sync_cancelled_total` — отменённые upstream-запросы.
- `spoke_sync_upstream_seconds` — время Electric с учётом idle polling, разбивка по ресурсу/статусу.
- `process_resident_memory_bytes`, `process_cpu_seconds_total` — процесс API; остальные контейнеры смотреть отдельно.

По умолчанию `SYNC_MAX_CONNECTIONS=128`, `SYNC_ADMISSION_TIMEOUT=0.25`. После четверти секунды ожидания proxy отвечает **503 + Retry-After: 1**. Это конфигурационный предел одновременных upstream-запросов, а не измеренная производительность. Например, 40 независимых устройств × 4 долгих подписки могут упереться в 128 ещё при низкой загрузке CPU. Для эксперимента изменяйте лимит осознанно и фиксируйте его в результатах; не поднимайте его одновременно со всеми остальными параметрами.

Запросы авторизации используют пул SQLAlchemy, отдельный от httpx; этот пул тоже может стать узким местом. Метрики процесса и лимит слотов сейчас рассчитаны на **один uvicorn worker**, как в Compose. При нескольких процессах потребуется multiprocess-сбор Prometheus и понимание суммарного лимита.

## План эксперимента на VPS

1. Зафиксируйте CPU/RAM, версии/commit, лимиты контейнеров, объём данных, число shapes, сеть до генератора. Прогрейте стенд; запуск с пустой базой измеряйте отдельно от больших снимков.
2. Запустите `api`, затем `sync`, затем `e2e` с одинаковым объёмом данных и несколькими сочетаниями читателей/скорости. Начните, например, с 5 читателей и 2 записей/с, затем 10/5, 20/10. Каждую ступень держите несколько минут и повторите.
3. Определите свой критерий заранее, например p95 доставки < 500 мс и < 1% ошибок. Следите за p99, пропусками, lag генератора, CPU, RAM, сетевым трафиком, диском/WAL и очередью proxy. Маленький прогон на 5–20 записях не даёт надёжного p99.
4. Повторите с большим датасетом (`--keep`) и новым подключением читателей: начальный snapshot и рабочие дельты имеют разную стоимость.
5. Отдельно сравните браузерные `shared/direct`. Уменьшение подписок не гарантирует меньшую задержку каждого рендера — у worker есть копирование данных и доставка сообщений.
6. После нагрузки проверьте возврат active/CPU/RAM, восстановление после перезапуска Electric и сети. Нагрузка только на ваш сервер; публичных целей по умолчанию в скриптах нет.

## Развёртывание на VPS

Стенд остаётся **демо с открытым выбором пользователя без пароля**. Используйте синтетические данные и ограничьте доступ к стенду/генератору на время эксперимента. Это не готовая production-аутентификация.

На отдельном VPS, где 80/443 свободны, настройте DNS на сервер, выполните `make init` и задайте в `.env`:

```dotenv
APP_DOMAIN=spoke.example.com
APP_ORIGIN=https://spoke.example.com
APP_EXTRA_ORIGINS=
```

Секреты `make init` генерирует самостоятельно; локальный `.env` переносить не требуется.

```bash
docker compose -f docker-compose.yml -f docker-compose.vps.yml up -d --build --wait
```

Caddy получит публичный TLS-сертификат. Override требует современный Docker Compose с `!override` (2.24.4+). PostgreSQL, Electric и API остаются без опубликованных портов. `caddy_data` содержит сертификаты и приватные ключи: volume не публиковать. Все последующие команды Compose для этой установки должны использовать оба файла.

Если 80/443 уже заняты вашим Caddy, **не запускайте standalone override**. Оставьте базовый Compose на loopback 8097, задайте APP_ORIGIN публичному HTTPS-домену и добавьте в существующий Caddy сайт `spoke.example.com { reverse_proxy 127.0.0.1:8097 }`. Для Caddy в Docker loopback другой: подключите нужные сервисы к отдельной общей сети и проксируйте туда; не копируйте конфигурацию поверх соседних сайтов.

На машине генератора:

```bash
uv run scripts/benchmark.py --url https://spoke.example.com --mode e2e --readers 10 --rate 5 --duration 120
cd frontend
npm run bench:tabs -- --url https://spoke.example.com --tabs 10 --writes 30
```

## Что проверено локально

Это короткая проверка корректности инструментов, **не тест максимальной ёмкости**:

- 25 автоматических проверок: 12 серверных (включая реальное отключение через Caddy), 2 маппера, 11 браузерных.
- Chromium, HTTP/2, 10 вкладок одного пользователя, 5 записей: shared — 4 исходные коллекции, direct — 40; в обоих случаях 50/50 появлений карточек, ошибок нет.
- Python, HTTPS + HTTP/1.1, 3 независимых читателя, 2 записи/с в течение 8 секунд: 16/16 записей, 48/48 подтверждений txid, пропусков и ошибок нет. В этом конкретном прогоне p95 API 15 мс, p95 доставки 17 мс; выборка слишком мала для вывода о предельной производительности.
- При обрыве настоящего long poll через Caddy active уменьшается с 1 до 0, cancelled увеличивается на 1.

Не смешивайте эти числа с ранними экспериментальными прогонами httpx/HTTP2: те воспроизводили задержки клиента и сохранены отдельно в локальных `.artifacts`.
